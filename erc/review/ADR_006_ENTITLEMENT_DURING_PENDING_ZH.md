# ADR-006　pending 期间的权益处理:可延期权利与不可延期权利

日期：2026-08-29
状态：草案，待确认
来源：业务方裁定，结合 HKEX / CCASS 规则核实

## 背景

HKEX 的行权日一般在除权日之后（> n），因此**权益判定点不会落在交收窗口内** —— 该问题在传统市场被日历设计规避掉了。权益完全由记录日当天的股东名册决定，交收期间不暂停任何权利。

本协议无法照搬：远端登记的完成时点与权益日历彼此独立，**权益判定点可能落在 pending 窗口内**。此时链上持有人是临时的，链下所有权人尚未确认，无法判定谁是正当权利人。

## 决策

按**该权利能否在事后以等效方式行使**，分为两类，分别处理：

### 一、不可延期权利（perishable）

典型：投票权。投票窗口关闭后无法追溯行使。

**规则**：pending 期间该权利暂停。新旧持有人**均不得**行使。

**理由**：无法判定正当权利人时，让任一方行使都可能是错的。**两方都不行使是唯一公平的结果。** 该次权益因此灭失，这是无法判定归属时的诚实代价，不应通过猜测归属来掩盖。

### 二、可延期权利（deferrable）

典型：分红、分配、赎回。价值可在事后以等效方式交付。

**规则**：pending 期间首次分配失败**不构成权利灭失**。pending 解除、确认持有人确定之后，正当权利人可发起**补行权（make-good claim）**取得该次权益。

**理由**：价值可延后交付，因此正确做法是延期而非灭失。

**受益人与交付方式（2026-08-29 补充）**：补发的收益记入**该权益基准时刻的权利人钱包**，即登记本在该时刻记载的权利人，**而非索赔时的当前 Token 持有人**。

因此权益跟随**当时的权利人地址**，不跟随 Token。该权利人此后即使已卖出 Token，仍取得该次分配 —— 与 HKEX 记录日语义一致，卖方保留除权前的权益。这同时消除一种套利：在 pending 期间买入无法截取窗口内的分配。

**两阶段解析（实现要点）**：权益事件发生时仍处于 pending，登记本**尚不知道**基准时刻的权利人是谁，因此此刻无法记录一个地址。正确做法是分两步：

1. **登记阶段**：按 `(tokenId, 权益标识, 基准时刻)` 记录一笔**未解析**的递延权益，此时不绑定地址；
2. **解析阶段**：证明到达、该时刻的已确认持有人确定后，该笔递延权益解析为具体地址并可被领取。

实现若在第一步就试图写入地址，必然写错 —— 那个地址在当时不可知。

**证明始终未到达的终止规则**：若交割在 deadline 后被取消，登记本的**前一版状态维持有效**，窗口内的权益因此解析为**pending 之前的已确认持有人**。这使取消不再只是"解锁 Token"，而是"登记本前值成立"，与 BLOCKER-1 修复后的语义连成一致的整体。

## 归属规则（关键，2026-08-29 修订）

**归属规则不由本标准发明，而由该权益自身的条款决定。** 标准的职责是让那个问题**可被回答**。

若某项权益的条款规定"按登记时间确认权利"，则判定方式是：取该权益规定的**行权基准时刻**（例如 1 月 1 日 0 时 0 分 0 秒），查**登记本在该时刻记载的权利人**。

这里的"登记本"是**远端登记的已确认记录**，不是 `ownerOf`。因此：

- 权益判定读的是证书版本链：找出 `effectiveAt` 区间覆盖该基准时刻的那一版，其对应的**已确认持有人**即为权利人；
- `ownerOf` 是**可交易头寸**，T+0 即变；
- 两者在 pending 期间例行分歧 —— 这正是本提案所称的"链上链下差异性同步"。

由此，`effectiveAt` 不再是装饰性字段：**它就是远端登记的生效时刻**，是权益判定的时间轴。其单调不减的约束因此成为正确性要求，而非整洁性要求。

标准不得规定权益必须按登记时间判定（有的权益可能按交易日判定），只应规定：**若某权益按登记时刻判定持有人，本标准的实现 MUST 能对任意过去时刻给出可解析的答案。**

### 由此暴露的数据模型缺陷

`CertificateRecord` 当前字段为 `certificateHash`、`previousCertificateHash`、`authorityReference`、`version`、`effectiveAt`、`supersededAt` —— **不含持有人**。

已确认持有人目前只存在于 `ownerOf`（仅当前值）与 settlement 记录的 `to`（逐笔）。链下索引器可从 `SettlementFinalized` 与 `Transfer` 事件重建，但**链上的权益合约无法查询**。

而补行权与记录时刻判定都必须在链上完成。因此：

- `CertificateRecord` MUST 增加已确认持有人字段；
- 需要一个按时刻解析的访问器（例如给定时间戳返回该时刻的已确认持有人与版本）。

**影响：这会改变 `0xebaa86a0`。** 加上此前认定会改变 `0x2773d4c9` 的各项，**两个 interface ID 都要重算**，应在同一轮内一次性完成。

## 对提案结构的影响

此项决策可能应当成为提案的中心，而非附加条款：

- 现有主张"证明门控的原子交割"较窄，且最近邻 ERC-7965 已占据同一语义空间；
- "**结算感知的权益生命周期：不可延期权利暂停、可延期权利延期并可追溯补行权**"目前**未发现任何对应先例**（ERC-7765 定义权利可否行使，ERC-5496 定义权利分离与到期，均未定义权利状态如何随结算状态变化，也未定义补行权）；
- 若以此为中心，证书版本链不再是"作者自述非主要贡献"的累赘，而是**补行权据以判定归属的已确认持有人期间账本** —— 一并解决此前 MAJOR-2 的结构质疑。

## 待确认问题

1. **分类由谁判定**：建议由权益合约自行判定并声明，本标准只按"能否事后等效行使"给出规范性定义，不枚举权利类型（保持资产中立）。
2. **本标准对权益合约的义务边界**：仅暴露状态与历史归属查询，还是同时定义补行权的登记与索赔接口？后者范围更大但更完整。
3. **历史归属查询**：补行权必须能问出"某时点的已确认持有人是谁"。当前接口无此能力（此前记为 MAJOR-3）。此项与本 ADR 是同一需求的两面。
4. 归属规则采用"追溯确定"是否为业务方本意 —— 本文按此草拟。

## 影响

采纳将改变 `0x2773d4c9`，并可能改变提案标题、Abstract、Motivation 与新颖性论证。应与 MAJOR-2、MAJOR-3 在同一轮内一次性定案，避免二次改接口。
