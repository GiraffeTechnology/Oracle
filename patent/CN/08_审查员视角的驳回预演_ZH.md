| 方向 | 为什么审查员一定会去 | 检索式 |
| --- | --- | --- |
| **双时态数据库(bitemporal)** | 本申请的 `effectiveAt` 就是 valid time，链上写入时刻就是 transaction time,`entryAsOf` 就是 as-of 查询。**这是本申请最危险的一块，原报告完全没查** | `bitemporal “valid time” “transaction time” “as of” append-only ownership` |

## 二、新检出的对比文件

### D12 —— US 11,935,046 B2 / US 2022/0284422 A1
**《Immutable database for processing retroactive and historical transactions using bitemporal analysis》**

这是本轮**最重要的检出**，也是原报告漏掉的最近邻的另一支。它公开了：不可变、只增的双时态账本；记录带 `valid from` 与 `created at` 两个时间；按时间序列维护历史；支持追溯交易。

#### D12 的逐字引用（答复时直接引这三段，不要转述）

审查员若以 D12 提创造性质疑，**反向教导的证据就在 D12 自己的文本里**。以下三段为逐字引用：

**引用一 —— 生效时间可以早于写入时间（打掉“严格递增是常规限制”）:**

> “a retroactive transaction 430 may be defined by temporal metadata 440 that includes a **'valid from' time 442 that is prior to a 'created at' time 444**.”

并定义：

> “the term '**retroactive transaction**' refers to a transaction that has an impact that is to be applied **retroactively** with respect to the current time and/or the 'created from' time of that transaction.”

**引用二 —— 更正手段是复制、替换、重放（证明其技术贡献恰在追溯写入本身）:**

> “**duplicating** the first temporal sequence of historical transactions to a second time-ordered sequence to form an alternate sequence of transactions in the second time-ordered sequence, **replacing** the historical transaction with the retroactive transaction in the second time-ordered sequence, and **replaying**, in the second time-ordered sequence, the second temporal sequence of historical transactions using the retroactive transaction to form a second alternate sequence of transactions including an alternate transaction.”

**引用三 —— 它把追溯写入当作优点（证明本领域无禁止它的动机）:**

> “**alternate timelines allow** the immutable database to **provide insight into how changes to already processed transactions (or events) in the system could affect the current state of the system**.”

**这三段合起来的效力：** D12 花全部篇幅实现的，正是本申请明令禁止的那件事，并且明确把它称作能力(“allow ... provide insight”)。本领域技术人员由 D12 出发，**没有任何动机**去禁止他刚刚实现的能力。这不是本项目的解读，是 D12 的原文。

> **使用前必须核实的一点**：上述三段引自 Google Patents 页面，措辞可靠；但**权利要求 1 的完整文本本轮未能逐字取得**（USPTO PDF 端点返回 403）。答复前须调取授权文本逐字核对权利要求 1，再行引用。**不要在答复中凭本文件转述权利要求 1。**

逐项核对：

| 特征 | D12 |
| --- | --- |
| 只增序列 + valid time + as-of 查询 | **公开**。这是双时态数据库的定义性特征 |
| 生效时刻严格递增 | **明确相反**。D12 的 `valid from` 可以早于 `created at`，并以此为卖点(“retroactive transaction ... valid from time that is prior to a created at time”) |
| 终局性判据 | **无**。备用时间线可以被无限次“提升”为当前线，过去状态永远可被改写 |
| 远端状态根成员证明 / 提交者不可信 | **无**。只提到本地写前日志的“cryptographically verifiable log files”，无分布式共识、无远端见证 |
| 待定期间数据凭证仍可转移 | **不涉及**。D12 是数据库与资源调度，不涉及数据凭证 |

**这既是最强的攻击，也是最强的防守。**

- 攻击面：F1（只增条目 + 生效时刻 + 按时刻查询）**必须承认已被 D12 公开**。原报告把 F1 当作“部分公开”是低估了。
- 防守面：D12 的核心手段是**允许追溯写入并以复制+重放来纠正**，与不变量 3（生效时刻严格递增，禁止任何后到条目落在已有条目之前）**直接冲突**。双时态领域把“能往 valid time 的过去写”当作能力而非缺陷；本申请把它当作必须禁止的东西，并且正是因为禁止了它，终局性才可判定。**这是教科书意义上的反向教导。**

### D13 —— 跨链桥证明绑定与防重放（公知常识，非单一文献）

本轮检索显示，下列做法在跨链桥安全领域属于**公知常识**，有大量公开技术文献与审计清单记载：

- 以 EIP-712/EIP-191 域分隔把签名绑定到 `chainId`，使一条链上的签名在另一条链上无效；
- 意图承诺中包含**目的链 ID 与具体合约地址**，以防同一份 fill claim 在另一条链的部署上被重放；
- 每条被见证的消息携带唯一 nonce 或内容哈希，合约在首次处理时记为已消费，其后拒绝。

**结论：F4 的“绑定目的侧字段”与 F5 的“消费标记、高度递增”应当整体承认为公知常识。** 原报告 §4.1 只说 D1 未公开这些，是把“最接近的现有技术未公开”误当成“不属于公知常识”——**这两件事不是一回事**，而审查员是可以直接引公知常识的。

### D14 —— SQL:2011 应用时间周期表（非专利文献，公知）

SQL:2011 标准引入 application-time period tables 与 system-versioned tables，行带 `(start, end)` 周期，支持按时刻查询。**这是“按生效区间解析某时刻的值”的标准化公知技术。** 与 D12 同属一族，同样不含终局性判据，同样允许在周期上做 `FOR PORTION OF` 的追溯改写。

> **诚实标注**：本条依一般技术常识列出，本轮**未抓取标准原文核对**。若审查员据此发意见，须先核原文再答复。

### D15 —— DTCC 数据凭证化托管（检索到但不构成对比文件）

DTC 的代币化试点把已托管的证券权益铸成代币，代币是向 DTC 发出记账指令的**另一种方式**，官方账簿仍是 DTC 的中心化账簿。**它不构造可按时刻解析的历史，也不给终局判据。** 本轮**未检索到**关于“记录日权益归属与未交收头寸”的对应专利文献；这是检索的空白，不是排除。

## 三、若我是审查员，第一次审查意见通知书会这么写

### 3.1 关于客体(《专利法》第二十五条第一款第（二）项、第二条第二款)——**最可能被发的一条**

> 权利要求 1 请求保护的方案，其发明点在于对一组数据记录施加若干写入约束（版本递增、时刻递增、承诺不重复）并据此回答查询。所述约束的实质是人为规定的记账规则，所解决的是记账结果的确定性问题，并非利用自然规律解决技术问题，故不属于专利法第二条第二款所称的技术方案。

**这一条能不能挡住：能，但必须靠说明书，不能靠权利要求的措辞。**

答复要点（说明书均已具备，注明段号）:

1. **技术问题是链上链下状态不一致**，不是记账规则的选择。见 [0003]–[0009]。
2. **技术手段包含大量非人为约定的成分**：密码学承诺、加标签的默克尔成员证明与索引位耗尽约束、经域分隔的类型化摘要与门限签名验证、远端高度单调、证明消费标记、单事务原子写入。这些是对计算机系统内部执行机制的改造，不是业务规则。见权项 S4、S5，说明书 [0018]、[0051]–[0058]。
3. **技术效果可客观验证**：终局性判定为常数时间；单个提交者无法伪造或重放准入；待定期间不冻结转移。见 [0023]–[0028]。
4. 权利要求 1 的前序即限定“由部署于区块链上的合约执行”，执行主体是计算机系统，不是人。

**风险评估：中等偏高。** 这一条即使答复成功也很可能来回两次。**不要在提交前为它改动权利要求**——现在改只会拖延，而客体问题在答复阶段处理是常态。

### 3.2 关于创造性（第二十二条第三款）——**最实质的一条**

我会这样组织：

> 对比文件 1(D12)公开了维护只增的双时态记录序列、每条记录带生效时间、并支持按时刻查询数据状态，即公开了权利要求 1 的 S1 与 S6 的查询部分。
>
> 权利要求 1 与 D12 的区别在于：(a) 生效时刻严格递增；(b) 记录承诺在凭证内唯一；(c) 终局性判定；(d) 待定窗口与凭远端证明的准入；(e) 待定期间不阻断转移。
>
> 其中 (d) 属于跨链证明验证领域的公知常识（见 D13）,(b) 属于防止记录重复的常规手段。区别 (a) 是本领域技术人员在需要保证记录顺序时容易想到的常规限制，而 (c) 是 (a) 的直接数学推论，不具有创造性。

**这条里唯一真正危险的是“(a) 是常规限制、(c) 是 (a) 的推论”。** 必须正面打掉，答复要点：

> **说明书对应段落（答复时逐条引用，不要临场组织）:** 代价与收益的完整论述在说明书 **[0025]–[0036]**；其中 [0025] 界定禁止的内容，[0026]–[0028] 逐项列出三项代价（失去追溯更正、错误留在记录上、某些迟到登记永久无法入账）,[0029]–[0031] 列出换得的三项性质，**[0030] 是最关键的一段**——它论证若不施加该禁止则终局性判据在原理上不存在；[0032] 说明该取舍为何在本场景中值得；[0033]–[0036] 是不阻断转移一侧的同构论述。说明书 **[0083]** 给出一个坐实该取舍的具体数值例子。背景技术 **[0009]–[0010]** 已记载双时态一族的做法及其为何不能解决本问题。

1. **(a) 不是常规限制，而是与 D12 所属领域的技术教导相反的限制。** D12 及整个双时态数据库领域（含 D14）把“能够向 valid time 的过去写入”作为**核心能力**;D12 的权利要求 1 的全部技术贡献就是如何做这种追溯写入（复制序列 → 替换 → 重放）。本领域技术人员由 D12 出发，**没有任何动机**去禁止他刚刚花全部篇幅实现的能力。

2. **(c) 不是 (a) 的推论，而是 (a) 的目的。** 逻辑方向要说清楚：不是“因为定了 (a) 所以顺便得到 (c)”，而是“因为需要一个可判定的 (c)，所以必须付出 (a) 的代价”。

   更强的一步在说明书 **[0030]**:**若不施加该禁止，该判据在原理上不存在**。设允许某条后到条目携带早于最新条目的生效时刻，则对任意过去时刻 t，总存在一条尚未到达的条目可能覆盖 t 处的答案，于是没有任何 t 可被判定为“答案不再改变”，终局性谓词恒为假；唯一的替代是引入一个人为约定的等待期限，但那是约定而非由记录导出的事实，且在登记簿确实迟到超过该期限时会给出错误结论。**因此不变量③不是优化，而是判据存在的必要条件。** 一个“必要条件”不可能同时是“容易想到的常规限制”——若它常规，则本领域早就应当具备该判据，而 D12 与 D14 都不具备。

   代价是实实在在的，说明书 [0026]–[0028] 逐项写明，其中 [0028] 承认一个不可恢复的后果：若已有生效时刻为 t2 的条目被准入，则登记簿在 t1 < t2 处的变更再也无法入账。**答复时应主动引用这一条**——一个方案敢于在说明书中写明自身的不可恢复代价，恰恰说明该取舍是经过权衡的设计选择，而非事后拼凑的区别特征。

3. **(e) 与 (d) 在现有技术中被当作互斥。** D1（过户代理协议）把链下手续归为 non-routine transfer 顺序处理；通行工程做法是冻结。本申请通过把“可转移归属”与“确认权属人”显式分为两个并存的所有权概念（S7 末句），同时取得二者。

4. **“最接近的现有技术”的选择本身可争。** D12 属于数据库领域，与本申请所属的区块链链上链下状态同步领域**技术领域不同、所要解决的技术问题不同**。若审查员以 D12 为最接近现有技术，可先争这一点；但**不要把答复押在这一点上**——审查员很可能改用 D1 为最接近现有技术、D12 为结合文献，那时上面第 1、2 点仍然成立。

**风险评估：中等。** 第 1、2 点是硬的，因为 D12 的权利要求原文自己写着追溯写入。

## 四、结论：哪些主张应当放弃，哪些必须守住

**放弃（不要在答复中坚持，坚持只会削弱可信度）:**

- F1 的“只增 + 生效时刻 + 按时刻查询”——D12 与 D14 已公开；
- F4 的“绑定目的侧字段”与 F5 的全部——跨链桥领域公知常识；
- EIP-712 域分隔、Merkle 标签化、索引位耗尽、低 s 值、签名人去重——公知。

**守住（全部创造性都在这四条上）:**

1. **生效时刻严格递增**，且这是与 D12/D14 的技术教导**相反**的限制；
2. **终局性判定**，它在允许追溯写入的现有技术中根本不存在，也不可能存在；
3. **待定期间不阻断转移**，配合“不由 `ownerOf` 推断确认权属人”这一双所有权概念的分离；
4. **推进权（核定权限主体）与 `ownerOf` 解耦并可读**。

**一句话版本：本申请的贡献不是“记录了历史”，而是“用放弃追溯改写能力换来了终局可判定，并且在付出这一代价的同时没有冻结市场”。** 答复时应当始终把论证拉回这一句。

## 五、建议在提交前做的唯一一处修改

**删除权利要求 14 的末句。** 修改后：

> **14.** 根据权利要求 1 或 3 所述的方法，其特征在于，还包括向外部合约提供彼此独立的三项查询结果，分别为：给定时刻的确认权属人、所述给定时刻是否终局、所述给定时刻是否被争议；所述三项查询结果不被合并为单一返回值。

理由：

- 保留的部分（“三项彼此独立、不合并为单一返回值”）**是**技术特征，限定的是接口形态；
- 删掉的部分（“不规定…处置方式”）**不是**技术特征，它描述的是本方案不做什么，既不缩小也不扩大保护范围，只会招来实施细则第二十条第一款的不清楚意见。

**这与 `06_...` §5.3 的说法相反，那里写着这句“是刻意的撰写选择，不应放弃”。** 那个判断只对了一半：该主张的**实质**（标准厘清谁有权定规则，而不代替其定规则）应当保留，但它的位置在说明书，不在权利要求。说明书 [0021]、[0066] 已经写明，答复客体质疑时从那里引用即可，不需要权利要求承载它。

**这处修改风险为零**（纯删除，不引入新内容，不缩小保护范围），耗时不超过五分钟，**不构成推迟提交的理由**。若时间紧张到连这一处也来不及，原样提交亦可——后果只是可能多收一次不清楚的审查意见，不影响申请日，也不影响新颖性与创造性。
